Challenge

Context

A growing product needed a shared language, not another layer of UI.

Freelancer's product surface had evolved across teams, platforms, and legacy patterns. Familiar interactions could behave differently, visual treatments drifted, and teams repeatedly solved the same interface problems.

The opportunity was to create a system that helped with day-to-day delivery, not a library that lived apart from the product. Bits needed practical building blocks while leaving room for the marketplace to evolve.

Findings

Key Insights

Platform was undergoing a large-scale migration from legacy web interfaces into a modernized and scalable design system

  • Legacy design system
  • UI files were disorganized across teams and products
  • Components behaved inconsistently
  • Design tokens were not consistently applied
  • Accessibility standards were not enforced
  • Engineers recreated UI patterns repeatedly
  • Documentation was either missing or outdated
  • Product teams moved quickly without scalable UI governance
  • Misalignment between design and production - there's a lack of various states, behaviours, and use cases.

The System

Architecture

Cross-functional alignment to make decisions

I mapped the system from foundations through component states and patterns, connecting visual choices to the workflows they needed to support. The map aligned design, engineering, and product around what belonged in the system and what remained product-specific.

That structure made Bits easier to navigate, contribute to, and apply consistently across the marketplace.

Sample structure of a UI component

Foundations

Shared primitives

Make the basics dependable before asking teams to scale them.

Typography, color, spacing, and responsive layout rules established the system's visual grammar. Tokens gave designers and engineers a common vocabulary, while documented rules made the intent behind each choice clear enough to use without guesswork.

This created a stable base for teams to compose new experiences without reintroducing visual debt.

Inclusive by default

Accessibility and internationalization

Accessibility and internationalization were part of the component contract.

A global marketplaceneeds patterns that remain understandable across languages, devices, and abilities. Bits documented accessible labeling, familiar icon use, contrast, focus behavior, and flexible layouts so teams could account for these needs from the beginning.

We made room for text expansion, regional formats, and right-to-left interfaces, turning international reach into a practical design constraint rather than a late-stage fix.

Design Guidelines

UI Components

I've contributed to writing the design guidelines for UI components like Forms. It collects input from users through elements like input fields, checkboxes, and radios. Clear labels, helpful placeholders, and actionable error messages keep forms easy to scan, fill, and recover from.

Learnings

Adoption depends on usefulness, not completeness.

The system earned trust by helping teams solve immediate, recurring product problems with clear and practical guidance.

Documentation is part of the product.

Guidance gave shared components context, helping teams understand when to use them and how to extend them responsibly.

Inclusion scales best when it is built into the defaults.

Accessible and localized patterns reduced the need to rediscover critical requirements late in delivery.
